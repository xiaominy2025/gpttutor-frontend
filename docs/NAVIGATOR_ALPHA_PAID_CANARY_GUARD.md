## Guard behavior

- Fixed run ledger row NAVIGATOR#CANARY#ALPHA-INITIAL at sk=STATE. It has no TTL, and must not be reset, overwritten, refunded, or replaced to rerun. It stores only approval ID/month, CAS version, phase, slot index, request and receipt hashes, token counts and microdollar holds/settlements. It does not store prompts, transcript, cookie, raw receipt or continuation.
- The guard receives the actual pinned runtime request, checks GPT-6 Luna Standard, 1,500 output tokens, no tools, and at most 12,000 UTF-8 bytes. It sends exactly those serialized bytes. The fixed conservative rates are $0.125/M input and $0.50/M output. At the ceiling each reserve is 2,378 microdollars and four reserves total 9,512 microdollars ($0.009512). The hard canary allowance is 30,000 microdollars ($0.03), subject to separate approval. Bounds are conservative ledger accounting, not an exact provider invoice.
- The pinned runtime first applies the canonical monthly reservation, visitor/IP limits and concurrency. The guard then claims a single slot with a conditional put, holds its reserve, and checks the canonical master again immediately before sending. A denied pre-dispatch attempt stops the run and retains the canary hold if created. The controller can definitively settle zero model spend in the canonical ledger when the guard never reached transport; possible dispatch, ambiguous usage or a hard crash retains conservative holds. The application makes one transport call without a retry. A concurrent duplicate cannot claim an already-held slot.
- A successful result with known usage, canonical settlement, valid guidance, and a committed canary settlement is required before the next step. Steps 2–4 also require the previous one-time receipt. If a successful accounting acknowledgement or invocation result is lost, a later controller cannot derive the receipt from the stored hash. Timeout, unverified usage, accounting failure, mismatched response metadata or out-of-bounds usage stops the run. Known usage is accounted for where settlement can be confirmed, and unknown usage keeps the hold. Crossing the approved UTC month cannot create another ledger or authorize another call.

## Operator journal

Use openCanaryJournal from server/platform/navigator-canary-journal.mjs around the one-attempt direct invocation callback. Use one designated, existing local journal directory for the exact approved run. The journal exclusively creates navigator-alpha-initial.ndjson and binds it to the reviewed source, manifest hash, ZIP SHA-256, and approval ID. The transport callback must independently verify the intended function and installed artifact against that binding and configure one invocation attempt with a finite timeout. The journal alone cannot verify what an injected callback actually invokes.

Each step is written and fsynced as pending before calling transport. A successful response must match the expected step, usage, cumulative spend, continuation and receipt shape, and final closure before the journal fsyncs a sanitized acknowledgement. The next step is otherwise unavailable. The callback receives the previous result in memory and can keep the cookie and synthetic transcript in its own memory for the next invocation. Neither the transcript nor any cookie, raw receipt, continuation, or raw error is written to the journal. On Windows the file is fsynced; directory fsync is added on platforms supporting that operation.

A lost result or acknowledgement, non-success, malformed response, expired approval window, or process restart stops the run. Any existing journal file, including an empty or partially written file, blocks re-opening. Do not delete, move, replace, or bypass that journal by using a different directory. Single-writer exclusion applies to the designated local file. The server's independent atomic slots still bound provider dispatch across clients. Do not perform another invocation after any uncertainty.

## Direct operator protocol, pending approval

1. Directly invoke the locked-down controller once with approval and step:0 to bootstrap a canary-specific anonymous cookie. No model credential is fetched for bootstrap. Step 0 returns a short-lived signed cookie for operator memory, derived under an acceptance-specific HMAC domain. It is unusable by the public Navigator. Keep cookie, continuation, full reply, and receipt in process memory, with no general-purpose debug logs.
2. Invoke step 1 with approval, step, cookie, and an empty history. Invoke steps 2–4 only after a confirmed successful result, passing the same cookie, committed history (fixed script user messages and successful assistant replies), continuation, and the previous receipt. The controller selects the fixed synthetic chemistry prompt for each step. Caller-supplied message text is rejected. Keep normal rate limits, including the two-per-minute limit, by pacing steps across minute buckets. Each HTTP or AWS SDK/CLI invoke must be configured for one attempt. Stop on the first non-success, timeout or unexpected response. Never repeat a step or restart a failed run.
3. Verify the fourth response closes the conversation. Read only sanitized usage/guard and canonical ledger evidence under authorized read permissions. Reconcile all confirmed attempts and unknown holds. Publish only redacted accounting and operational results. Record readiness limitations even if all four calls succeed.

The guard does not test real browser cookie behavior, viewer IP from CloudFront, or the effect of a real master OFF window. Its placeholder documentation-range IP deliberately exercises the existing canonical IP control in a direct invocation, without claiming real visitor attribution. The master stays ON unless separately authorized for a coordinated test. Effective raw-key compatibility and allowed model metadata remain owner-coordinated gates. Proposed paid scope is exactly this one approval-bound run, at most four sequential model requests, no retries and at most $0.03; no public activation or shared-control change is implied.
